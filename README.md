# BZShow ↔ iCloud Calendar

Серверное приложение для тестовой двусторонней синхронизации календарей Битрикс24 с iCloud. Портал определяется при установке через OAuth Битрикс24, без привязки к BZShow. Поддерживаются облачные порталы и порталы на собственных публичных HTTPS-доменах с действующей регистрацией REST-приложения. Регистрация в кабинете вендора используется для закрытого тестирования.

## Подключение

1. Установите и откройте приложение «iCloud Календарь» в своём Битрикс24. Сервер подтверждает портал и REST-адрес через OAuth-сервер Битрикса, затем проверяет профиль и код приложения. Входящий вебхук не требуется.
2. Введите свой Apple ID и отдельный пароль приложения, созданный в `account.apple.com`. Пароли и токены шифруются на сервере. Каждому сочетанию `member_id` портала и ID пользователя соответствует отдельная запись: другие пользователи и порталы не получают доступ к вашему подключению, календарным связям или результатам синхронизации. Сейчас поддерживается один Apple ID на пользователя в каждом портале, с несколькими календарями.
3. Отметьте календари галочками в списках «Из iCloud в Битрикс24» и «Из Битрикс24 в iCloud». Каждый календарь связывается с отдельным календарём на другой стороне. Единственное точное совпадение имени связывается автоматически; иначе создаётся календарь с тем же названием и цветом. Связь можно приостановить без удаления событий.
4. Сохраните выбор, просмотрите действия и нажмите запуск с включением автообмена. После первоначального подтверждения сервис работает на сервере без открытого браузера и включённого Mac. Новая пара календарей требует своего предпросмотра.

Выбор календарей Битрикса и переключатели существующих пар можно сохранить даже
при недоступности Apple. Такой выбор переживает перезагрузку страницы и пока не
создаёт календари в iCloud. После восстановления подключения снова нажмите
«Сохранить календари», чтобы применить его. До применения автообмен ожидает и
не переносит события. Переключатель автоматического режима доступен заранее:
его выбранное состояние сохраняется, а рядом отображается причина ожидания.
Фоновая запись разрешается только после первого подтверждённого запуска каждой
выбранной пары календарей.

Изменения iCloud проверяются каждые 5 секунд одним лёгким запросом ctag/sync-token без скачивания событий. Обрабатываются только изменённые выбранные календари. Неизменённые данные iCloud повторно используются из памяти только после проверки версии; ручной предпросмотр всегда читает свежие события. Уведомления Bitrix24 объединяются за 200 мс и направляются в нужную пару календарей по идентификатору события. Каждые 30 секунд выполняется резервная полная проверка, если уведомление потерялось; события выбранных календарей Битрикса читаются одним запросом. HTTPS-соединения повторно используются, ограничения частоты REST соблюдаются отдельно для каждого портала. Проверки одного пользователя не перекрываются.

Это не гарантия мгновенной доставки: длительность обмена, доступность Apple и ограничения API влияют на задержку. При ошибках включается увеличение интервала повторных попыток до 15 минут; HTTP 429/503 учитывает Retry-After. Успешное переподключение iCloud снимает старую паузу и сразу ставит обмен в очередь. Статус и последняя ошибка видны в приложении. По умолчанию автообмен выключен.

События ищутся за последние 7 дней и до выбранного горизонта (1–365 дней вперёд, по умолчанию 30). Создавать обычные события можно в любой выбранной паре в Apple или Bitrix24; копия попадёт в соответствующий календарь. Сопоставление событий из разных пар изолировано. При первом запуске одинаковые по названию и времени события внутри пары связываются, а не создаются заново. Если оба связанных события изменились, конфликт пропускается.

Удаления связанных событий передаются в обе стороны в пределах периода синхронизации. Пустой ответ диапазонной выборки не считается удалением: приложение отдельно читает событие по ID, а ресурс iCloud по URL. Ошибки доступа, некорректные ответы и перемещение в другой календарь останавливают удаление. Событие, перенесённое за границы периода, проверяется по сохранённой связи и не считается удалённым. Если оставшаяся копия изменилась после последнего обмена, создаётся конфликт. Перед удалением проверка повторяется; в iCloud используется If-Match/ETag. У Bitrix нет условного удаления по версии, поэтому остаётся минимальное окно между контрольным чтением и запросом удаления. После успеха связь снимается, а запись об удалении сохраняется в зашифрованном журнале последних 500 связей. Посторонние несвязанные события не удаляются.

Повторы iCloud разворачиваются библиотекой ICAL.js в отдельные встречи Битрикса в пределах периода, с учётом EXDATE, RDATE, исключений, переносов и часовых поясов. Идентификатор копии привязан к исходной дате повторения, а не к перенесённой дате. Название и время таких встреч редактируются в iCloud: правка копии в Битриксе становится конфликтом и не переписывает исходную серию. Удаление копии в Битриксе добавляет EXDATE для одного вхождения в iCloud, не удаляя всю серию. Исключение THISANDFUTURE сохраняется для будущих встреч. Отмена вхождения или удаление серии в iCloud удаляет соответствующие неизменённые связанные копии в Битриксе. Нативные серии Битрикса, события на весь день и приглашения из iCloud пока не переносятся. Встречи Bitrix с участниками можно скопировать в iCloud, но изменение или удаление их копии не переписывает и не отменяет встречу Bitrix. Перемещение существующего события между календарями и последующие переименования самих календарей автоматически не синхронизируются. В фоне показываются календарь загрузки и счётчик переноса; список последних действий сохраняется и после проверки без изменений.

## Отключение Apple

Кнопка «Удалить подключение iCloud» работает и при ошибке Apple, без обращения к CalDAV.
Перед подтверждением виден список календарей, созданных приложением в Битриксе.
Отдельная галочка разрешает удалить их вместе со всеми событиями, включая
добавленные вручную. Исходные и ранее существовавшие календари Битрикса не
удаляются; календари Apple никогда не удаляются. Если удаление не удалось,
автообмен останавливается, а подключение и оставшиеся связи сохраняются для
повторной попытки. После успешного отключения пароль и связи стираются из текущих
настроек сервиса. Зашифрованные резервные копии управляются отдельно.

Пароль в поле можно показать переключателем. Уже сохранённый серверный секрет
в браузер не возвращается. Пробелы и типографские дефисы при вставке нормализуются.
HTTP 401 от Apple не считается пустым списком календарей; повторные попытки с
другим паролем не вытесняют проверенный клиент из кеша.

## Развёртывание

Зависимости: Node.js 24, `npm ci`. Заполните серверный `.env` по `.env.example` и задайте случайный 32-байтовый ключ ENCRYPTION_KEY в base64. Запуск:

```sh
node --env-file=.env src/server.mjs
```

Подробности работающей установки, PM2, HTTPS и резервного копирования: [DEPLOYMENT.md](DEPLOYMENT.md).

Проверки:

```sh
npm test
```

Шифрованные данные находятся в `runtime/accounts/*.enc`. Сохраняйте их вместе с ключом шифрования. Потеря связей событий может привести к дублям при новом запуске. Старые `runtime/config.json` и `runtime/state.json` от прототипа на Mac сервером не используются. Пароли из Связки ключей macOS на сервер автоматически не переносятся.
